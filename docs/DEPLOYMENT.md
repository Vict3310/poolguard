# PoolGuard deployment guide

PoolGuard is an **experimental NEAR testnet application**. It is not audited, has no mainnet configuration, and all balances are test tokens with no monetary value. Nothing in this document is a claim that a deployment has already happened.

This guide covers:

1. Local PostgreSQL, with Docker or the embedded fallback.
2. Contract build and tests.
3. Sandbox integration proof.
4. Testnet infrastructure and account/key separation.
5. Environment variables and process startup.
6. Production hardening and explicit limitations.

For the local four-scenario walkthrough, see [DEMO.md](./DEMO.md).

---

## 2. Local PostgreSQL with Docker

The repository includes a local-only `docker-compose.yml` (PostgreSQL 18). Start it with:

```bash
docker compose up -d postgres
docker compose ps
```

The matching connection string is:

```text
postgresql://poolguard:poolguard@127.0.0.1:55432/poolguard
```

The credentials above are for local development only. Do not reuse them for a shared or public deployment. Data lives in the `poolguard-postgres` volume until `docker compose down -v`.

### Local PostgreSQL without Docker

On Linux x64, start the project-local server:

```bash
node scripts/local-postgres.mjs
```

It uses `.data/postgres`, listens on `127.0.0.1:55432`, and creates the `poolguard` database. Optional environment overrides:

```bash
LOCAL_PG_PORT=55432
LOCAL_PG_USER=poolguard
LOCAL_PG_PASSWORD=poolguard
LOCAL_PG_DATABASE=poolguard
LOCAL_PG_VERBOSE=1
```

The embedded binary package is Linux x64 only. macOS users should use Docker or a native PostgreSQL install.

## 3. Environment variables

There are three layers:

- `.env` — base settings and secrets, loaded by the API, worker, provider and seed script.
- `.env.testnet` — testnet overlay. It is loaded automatically after `.env` when present, or selected explicitly with `POOLGUARD_ENV_FILE=.env.testnet`; process environment values always win. It is gitignored; start from [`.env.testnet.example`](../.env.testnet.example).
- `.env.local` — generated by `node scripts/sandbox.mjs` for a **local sandbox only**. It is loaded only outside production/testnet; the services refuse to start if it exists in production/testnet mode. It is gitignored and contains local-only keys.

Never commit these files. Never put owner seed phrases in them. The owner's privileged key is not an application secret.

Use `.env.example` as the starting template when present:

```bash
cp .env.example .env
```

Then fill in the values. The complete set of names read by the services is below.

### Required backend variables

| Variable | Used by | Meaning |
|---|---|---|
| `DATABASE_URL` | API, worker, provider, Prisma | PostgreSQL connection string. |
| `NEAR_NETWORK` | all | `sandbox` or `testnet`. Mainnet is not supported. |
| `NEAR_RPC_URL` | all | NEAR JSON-RPC endpoint. |
| `POOLGUARD_CONTRACT_ID` | all | Deployed contract account. |
| `OWNER_ACCOUNT_ID` | API, worker | Task owner account. `POOLGUARD_OWNER_ACCOUNT_ID` is accepted as a fallback. |
| `PROVIDER_ACCOUNT_ID` | all | The payout recipient account, and the provider catalog owner. |
| `PROVIDER_ORIGIN` | API, provider | Base URL of the provider, e.g. `http://127.0.0.1:4103` or `https://provider.example.com`. |
| `PROVIDER_SERVICE_DOMAIN` | provider, worker | NEP-413 recipient domain for provider buyer auth. Host only, no scheme: `127.0.0.1:4103` or `provider.example.com`. |
| `API_ORIGIN` | web, API metadata | Public/API base URL. The Next.js rewrite defaults to `http://127.0.0.1:4100`. |
| `WEB_ORIGIN` | API | Browser origin. Its host becomes the NEP-413 sign-in domain and must match the page origin. |
| `SESSION_SECRET` | API | At least 32 characters. Generate a new random value per environment. |
| `DOCUMENT_ENCRYPTION_KEY` | API, worker | Base64 of exactly 32 bytes (`openssl rand -base64 32`). Encrypts document text at rest. |
| `WORKER_ONE_ACCOUNT_ID` | API, worker | Worker account one. |
| `WORKER_ONE_PRIVATE_KEY` | API, worker | Restricted function-call private key for worker one. |
| `WORKER_TWO_ACCOUNT_ID` | API, worker | Worker account two. |
| `WORKER_TWO_PRIVATE_KEY` | API, worker | Restricted function-call private key for worker two. |

| `SESSION_TTL_DAYS` | `7` | Wallet session lifetime, 1–30 days. |
| `PROVIDER_HOST` | `127.0.0.1` | Provider bind address. |

`SESSION_SECRET` and `DOCUMENT_ENCRYPTION_KEY` must not be reused between local, preview and production environments.

## 4. Database migrations and seed

Prisma CLI reads `DATABASE_URL` from the process environment. The root `.env` is loaded by the application scripts, but `prisma migrate` itself does not automatically read the repository-root file. Export the environment first:

```bash
set -a
. ./.env
[ -f .env.local ] && . ./.env.local
set +a

pnpm db:generate
pnpm db:migrate
pnpm db:seed
```

`pnpm db:migrate` is `prisma migrate deploy`; committed migrations live in `packages/db/prisma/migrations`. `db:seed` seeds the operator-controlled provider and the fixed catalog:

- `doc-extract` / `doc-extract-v1` — `0.02` testNEAR.
- `doc-summary` / `doc-summary-v1` — `0.005` testNEAR.

Both output the same bound supplier-extraction schema. Prices are fixed catalog prices, not cryptographically signed quotes.

For a destructive local reset only:

```bash
pnpm --filter @poolguard/db db:reset
pnpm db:seed
```

`db:reset` is `prisma migrate reset --force` and deletes all local data.

## 5. Contract build and tests

```bash
pnpm contract:build
pnpm contract:test
```

`pnpm contract:build` runs `scripts/contract-build.sh`:

- Checks for `cargo`.
- Adds `wasm32-unknown-unknown` if missing.
- Builds with `--locked` from `contracts/poolguard`, applying `.cargo/config.toml`.
- Writes `contracts/poolguard/res/poolguard.wasm`.

`pnpm contract:test` runs the Rust unit suite (`cargo test --manifest-path contracts/poolguard/Cargo.toml`). The suite covers owner authority, agent registration/revocation, wrong keys, provider allowlists, per-operation caps, shared-budget races, exact-boundary amounts, expiry, stale policy, changed-argument replay, duplicate execution, failed payouts, duplicate callbacks, withdrawals, cross-task isolation, bounded storage, integer checks and the conservation invariant.

`cargo-near` is optional; the contract is a plain `near-sdk` cdylib and the script does not require it.

### Sandbox integration proof

The sandbox proof is a Node script, not a mock:

```bash
node scripts/sandbox-test.mjs
```

It starts `near-sandbox`, deploys a freshly built WASM, creates real accounts with restricted function-call keys, and asserts finalized chain state for the important financial boundaries, including a concurrent reservation race, one payout, replay idempotency, unauthorized-provider denial and the accounting invariant. It tears the sandbox down at the end and does not write `.env.local` or touch the application database.

`pnpm contract:sandbox-test` runs the same Node proof. The current `near-api-js` + `near-sandbox` tooling is used instead of a Rust `near-workspaces` target; both drive a real node, and this avoids a second, divergent test harness.

## 6. Local sandbox deployment

```bash
node scripts/sandbox.mjs
```

This is a **local-only** provisioning command. It deploys the contract and writes `.env.local`; keep it running. It creates owner/provider/worker accounts, transfers sandbox NEAR, and adds restricted function-call keys to both worker accounts. The sandbox is ephemeral, so restarting it invalidates previous tasks and accounts.

Start the apps after the sandbox has written `.env.local`:

```bash
pnpm dev
```

The runner applies migrations/seed and starts the API, worker, provider and web app. If the runner is not available, use the manual layout in section 8. Do not run two worker processes with the same restricted key.

The browser uses the explicitly labelled sandbox session (`POST /dev/session`), which is available only when all of these hold: `LOCAL_SANDBOX_MODE=true`, `ALLOW_DEV_SESSION=true`, `NODE_ENV !== "production"`, and an owner account is configured. It is never a production wallet substitute.

## 7. Testnet deployment

For a reviewable end-to-end sequence, use [TESTNET_RUNBOOK.md](TESTNET_RUNBOOK.md).
The machine-checkable gate is `pnpm testnet:preflight` (read-only) and the live
service gate is `pnpm testnet:verify`.

### 7.1 Identities and authority

Use separate accounts:

| Identity | Purpose | Key location |
|---|---|---|
| Deployer / contract account | Hosts the PoolGuard contract and its storage/operational balance. | Deployer key offline or in a secured ops environment. Never in the app. |
| Owner account | Funds tasks, registers agents, sets policy, pauses/revokes, withdraws available funds. | Owner wallet. Owner seed/private key never reaches the API, worker, browser bundle or logs. |
| Worker one and worker two | Sign `reserve`, `execute`, `cancel_reservation`, `expire_reservation` for registered tasks. | Restricted function-call keys in worker/API runtime secret storage. |
| Provider account | Receives contract payouts and owns the revenue service catalog. | No application signing key needed to receive payouts. Keep any management key offline. |

The contract account's `owner` field is the deployer and has **no power over task funds**. Each task has its own owner. A worker key cannot invoke owner administration, attach NEAR, or pay an arbitrary recipient.

Function-call key allowance limits **gas spend**, not the task purchase budget. The task budget, per-operation cap, provider allowlist and reservation accounting are enforced in the contract.

### 7.2 Build and deploy the contract

Build locally:

```bash
pnpm contract:build
```

Using classic `near-cli` (verify syntax with `near --help` in your installed version):

```bash
# Create the contract account and deploy.
near create-account poolguard.testnet --masterAccount owner.testnet --initialBalance 20
near deploy poolguard.testnet contracts/poolguard/res/poolguard.wasm
near call poolguard.testnet new '{}' --accountId poolguard.testnet --gas 50
```

The contract's `new` takes no arguments. Keep the deployer/full-access key out of the application environment. The contract account needs enough balance for its own storage and operational costs; task budgets are separately deposited and accounted.

### 7.3 Create provider and worker accounts

```bash
near create-account extract.testnet --masterAccount owner.testnet --initialBalance 1
near create-account agent-one.testnet --masterAccount owner.testnet --initialBalance 2
near create-account agent-two.testnet --masterAccount owner.testnet --initialBalance 2
```

The provider account is a recipient; do not put a provider private key in the app.

For each worker, add a function-call key that can reach **only** the PoolGuard contract and only the worker methods:

```bash
near add-key agent-one.testnet "$WORKER_ONE_PUBLIC_KEY" \
  --contractId poolguard.testnet \
  --methodNames reserve,execute,cancel_reservation,expire_reservation \
  --allowance 0.25

near add-key agent-two.testnet "$WORKER_TWO_PUBLIC_KEY" \
  --contractId poolguard.testnet \
  --methodNames reserve,execute,cancel_reservation,expire_reservation \
  --allowance 0.25
```

`$WORKER_ONE_PUBLIC_KEY` and `$WORKER_TWO_PUBLIC_KEY` must be the public keys derived from `WORKER_ONE_PRIVATE_KEY` and `WORKER_TWO_PRIVATE_KEY`. If they do not match, the contract rejects the worker with `AGENT_KEY_MISMATCH`. Once the API is running with the worker secrets configured, `GET /meta` returns the derived `workerAccounts[].publicKey` values; use those exact strings. Public keys are not secrets.

After adding the restricted keys, remove any full-access key from the worker accounts and keep recovery keys offline:

```bash
near delete-key agent-one.testnet "$WORKER_ONE_FULL_ACCESS_PUBLIC_KEY"
near delete-key agent-two.testnet "$WORKER_TWO_FULL_ACCESS_PUBLIC_KEY"
```

Do not give a worker key owner methods such as `pause_task`, `update_policy`, `register_agent`, `revoke_agent` or `withdraw_available`. Do not use an owner account as a worker account in this MVP.

### 7.5 Create and fund tasks

Normal task creation goes through the owner wallet in the UI:

1. Create the task metadata and documents in the app.
2. Review the server-built setup plan.
3. Sign one owner transaction containing `create_task`, `fund_task`, and both `register_agent` calls.
4. The API confirms the transaction against finalized chain state before marking the task active.

This owner setup transaction is separate from worker operations. It attaches storage deposits and budget; worker function-call keys cannot attach NEAR. Storage deposits are 0.35 NEAR for a task and 0.02 NEAR per agent in the current contract, non-refundable in this MVP (any amount attached above them is refunded). The task budget is additional and remains spendable under policy.

If you use classic `near-cli` for an infrastructure smoke test instead of the UI, use the exact contract argument shape:

```bash
near call poolguard.testnet create_task \
  '{"task_id":"manual-smoke","name":"Manual smoke","policy":{"max_per_operation":"20000000000000000000000","allowed_providers":["extract.testnet"],"reservation_ttl_blocks":300,"expires_at_block":<CURRENT_BLOCK_PLUS_MARGIN>}}' \
  --accountId owner.testnet --deposit 0.35 --gas 50

near call poolguard.testnet fund_task '{"task_id":"manual-smoke"}' \
  --accountId owner.testnet --deposit 0.03 --gas 50

near call poolguard.testnet register_agent \
  '{"task_id":"manual-smoke","account_id":"agent-one.testnet","public_key":"ed25519:..."}' \
  --accountId owner.testnet --deposit 0.02 --gas 50
```

`expires_at_block` must be an actual future block height, not the placeholder. A manual CLI task has no database row, so the application will not display it and the worker will not run against it; use the UI for an application demo.

Verify chain state:

```bash
near view poolguard.testnet get_task '{"task_id":"manual-smoke"}'
near view poolguard.testnet get_policy '{"task_id":"manual-smoke"}'
near view poolguard.testnet get_budget '{"task_id":"manual-smoke"}'
near view poolguard.testnet get_config '{}'
```

## 8. Running the apps

### Local runner

```bash
pnpm install
node scripts/sandbox.mjs   # separate terminal, local sandbox only
pnpm dev
```

The runner starts the app processes after migrations/seed. If you use a Docker database, start it first.

### Run the local apps manually

If you need separate lifecycle control, for example to restart the worker during scenario D:

```bash
# Terminal 1: PostgreSQL, unless already running
node scripts/local-postgres.mjs

# Terminal 2: local NEAR sandbox
node scripts/sandbox.mjs

# Terminal 3: migrate and seed
set -a
. ./.env
[ -f .env.local ] && . ./.env.local
set +a
pnpm db:generate
pnpm db:migrate
pnpm db:seed

# Terminals 4–7: one process each
pnpm dev:api
pnpm dev:worker
pnpm dev:provider
pnpm dev:web
```

Only one worker process may sign with a given restricted key at a time. If you stop and restart the worker, let the old process exit first.

### Production-style build and start

```bash
pnpm install --frozen-lockfile
pnpm build

pnpm --filter @poolguard/api start
pnpm --filter @poolguard/worker start
pnpm --filter @poolguard/provider start
pnpm --filter @poolguard/web start
```

Run migrations and seed before starting the API/worker. The web build needs `API_ORIGIN` set at build time if the API is not on the default local origin.

Health endpoints:

- API: `GET /health`, `GET /ready` (database and RPC checks).
- Provider: `GET /health`, `GET /ready` (database check).
- Web: `GET /` and a page render.

There is no built-in process supervisor, metrics backend, alerting stack or dashboard in this MVP. Use your platform's supervisor and log collection.

## 9. Setup transactions versus normal worker operations

Keep these paths separate in operations, logs and access reviews.

### Owner setup/administration

Signed by the owner wallet:

- `create_task` with the task storage deposit.
- `fund_task` with the task budget.
- `register_agent` with a storage deposit.
- `update_policy`, `revoke_agent`, `pause_task`, `resume_task`, `withdraw_available`.

The backend builds the transaction plan but never receives owner signing authority on testnet. The local sandbox helper is the only place that signs owner setup, and it is gated off outside sandbox mode.

### Worker operations

Signed by the registered worker's restricted function-call key:

- `reserve` before any purchase.
- `execute` to dispatch the one payout.
- `cancel_reservation` before dispatch.
- `expire_reservation` for eligible expired reservations.

Worker keys cannot attach NEAR, fund a task, register another agent, change a policy or withdraw. Function-call allowance is gas-only.

### Contract callbacks

`on_payout_complete` and `on_withdrawal_complete` are private callbacks. They are callable only by the contract account, are idempotent, and are the only path that finalizes a pending transfer. A timeout is never treated as a failed transfer.

## 10. Production hardening

Required before exposing anything beyond a local demo:

- **Use testnet only.** `NEAR_NETWORK` is restricted to `sandbox` and `testnet`; there is no mainnet path.
- **HTTPS everywhere.** Cookies become `secure` when `WEB_ORIGIN` starts with `https://`. Terminate TLS at a trusted proxy or the app, and verify redirects/origins end to end.
- **Disable dev sessions.** `NODE_ENV=production`, `LOCAL_SANDBOX_MODE=false`, `ALLOW_DEV_SESSION=false`. The API refuses to start in production with `ALLOW_DEV_SESSION=true`.
- **Disable fault injection.** `FAULT_INJECTION_ENABLED=false` outside scripted demos.
- **Remove sandbox owner authority.** Unset `SANDBOX_OWNER_PRIVATE_KEY`; do not copy `.env.local` to a server.
- **Rotate secrets.** Generate `SESSION_SECRET` and `DOCUMENT_ENCRYPTION_KEY` per environment. Store them in a secret manager, not in an image or repository.
- **Restrict worker keys.** Function-call keys only, PoolGuard contract only, only `reserve`, `execute`, `cancel_reservation`, `expire_reservation`. Keep full-access worker keys offline.
- **Keep owner/deployer keys offline.** The owner's wallet key is the financial authority. The deployer key can upgrade/replace the contract account; protect it accordingly.
- **Protect the database.** TLS, least-privilege credentials, backups, restricted network access, encrypted volumes. The database is a projection and coordination store, not the financial authority.
- **Review proxy behavior.** Set `API_TRUST_PROXY` to the proxy IP/CIDR (or a comma-separated list) that matches the topology. Leaving it `false` makes every request appear from the proxy and collapses the rate limit; setting it to `true` trusts arbitrary forwarded addresses. Hop counts are rejected because they let direct clients spoof forwarding headers. Never expose the API except through the trusted proxy when forwarded headers are trusted.
- **Do not scale one worker key horizontally.** NEAR requires monotonic nonces per key. Run one process per key, or shard keys deliberately.
- **Monitor the provider and worker.** A paid operation with missing delivery is valid but incomplete. Alert on `needsRecovery`, `PAYOUT_PENDING`, failed jobs and provider `/ready` failures.
- **Review rate limits and body limits** for your traffic. The provider has a global 180 requests/minute limit plus tighter quote/purchase limits; the API has its own limits. These are prototype defaults, not a capacity plan.
- **Add a CSP and security headers at the edge.** The app sets several basic headers and `poweredByHeader: false`, but does not ship a complete CSP.
- **Run the deployment gates.** `pnpm testnet:preflight` must pass before services are exposed, and `pnpm testnet:verify` must pass against the public origins. Treat warnings as review items, not silent acceptance.
- **Do not describe the result as audited or production-ready.** It is an experimental testnet prototype.

### Known deployment limitations

- No mainnet support, custom tokens, stablecoins, chain signatures, trading or dispute arbitration.
- No custom authentication system; NEAR NEP-413 sessions are used, with a sandbox-only development session.
- Provider prices are fixed operator-controlled catalog prices, not signed quotes.
- Exactly-once across an on-chain transfer and an off-chain service is not promised. The design target is at-most-once payout through the contract, plus provider deduplication and stored, recoverable results.
- A provider result is stored in the shared application database; provider availability and database durability are operational dependencies.
- No automated secret manager, process supervisor, metrics or alerting integration is included.
- The embedded PostgreSQL helper is Linux x64 only.

## 11. Fresh-checkout rehearsal

```bash
pnpm install --frozen-lockfile
pnpm contract:build
pnpm contract:test

# Start PostgreSQL (Docker or embedded), then:
node scripts/sandbox.mjs          # local economic proof, separate terminal
```
